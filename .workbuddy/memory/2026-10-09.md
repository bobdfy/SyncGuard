## SyncGuard 项目全面分析（应用户要求以资深 Go 工程师视角）

**验证结果**：`go build ./...` 通过；`go vet ./...` 通过（EXIT=0）；`go test ./...` 全部 ok（含集成测试，本地 PG 可用）。

**项目概况**：分布式数据同步系统，Go 1.26 + Gin + pgx + RabbitMQ + Redis。Server/Worker 双进程，Transactional Outbox、Redis 分布式锁+心跳续约、三态熔断、指数退避重试+DLQ、双轨道（信封/原表镜像）、数据对账、多用户 JWT 隔离。架构与代码质量较高。

**识别的问题/改进方向**：
- Handler.Handle 近 300 行，「记 pending + 写 outbox + 提交事务」样板代码重复 3 次，应抽取 `retryLater(job, delay, reason)` 帮助函数。
- 全局 `log.Printf`，无结构化日志/request_id 串联。
- `godotenv.Load()` 返回值未处理；main 只有 os.Interrupt，缺 SIGTERM；Worker 退出时不等待在途消息处理完。
- Server 对账接口同步执行，大表全量加载进 map，会阻塞 HTTP worker 且内存 O(n)。
- 安全性：JWT 无过期/无登出失效机制；connections.source_url 明文存连接串密码；无限流/CORS/安全头。
- 并发：Worker prefetch=1 单消息串行处理，扩并发需评估。
- DLQ 无消费者、无查询 API/告警。
- 建议方向：MySQL 数据源（Roadmap 已列）、定时全量对账 automation、Prometheus 指标。

**下一步计划（已给用户）**：P0 重构 worker.Handle 样板+结构化日志；P1 优雅退出/配置校验/安全加固；P2 对账异步化+DLQ 管理；P3 新数据源 MySQL/Kafka。
