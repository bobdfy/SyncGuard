## 二、逐文件复盘（01–41）

### 第 1 层：入口装配

**01 · cmd/server/main.go（95 行）— HTTP 服务的装配根**
- 启动链路：加载 `.env` → 校验 `JWT_SECRET` 非空（空值直接拒绝启动）→ 连 PG → 建 4 个 Store → 建对账引擎 → 连 RabbitMQ → 建 Producer → 建 3 个 Handler → 注册路由 → 挂静态页 → 优雅退出。
- 路由分两组：公开（register/login）和 JWT 鉴权组（数据源 CRUD、任务 CRUD、run、reconcile、records）。
- 注意点：Handler 结构体里直接塞具体 Store/Producer 类型（未接口化，这是 handler 难单测的根源）；`r.StaticFile("/", ...)` 把登录页挂在根路径。

**02 · cmd/worker/main.go（102 行）— Worker 进程的装配根**
- 启动链路：连 PG / RabbitMQ / Redis → 建连接级分布式锁 → 为**延迟重投单独开一个 channel** 并开启 publisher confirm（保证"延迟消息被 Broker 确认后才算发出"）→ 建 Producer / Consumer（QoS=1）→ 建 Dispatcher（outbox 搬运工）和 Handler → dispatcher 用独立 ctx 后台跑 → 主循环 select quit/msgs。
- 注意点：消息循环里 `h.Handle(msg)` 是同步阻塞的，配合 QoS=1 实现"一个 Worker 同时只处理一个任务"。

### 第 2 层：领域模型

**03 · internal/model/record.go（20 行）— 全系统"数据通货"**
- `Record{ID, Version, UpdatedAt, Data(JSONB)}`，任何数据源都要把数据转成这个结构才能进引擎。Data 用 `json.RawMessage` 保留原始形状。

**04 · internal/model/job.go（21 行）— 同步任务 + 断点状态**
- 状态机：`pending / running / completed / failed`；`Cursor` 是断点游标；`TargetConnectionID *int` 可空——**nil = 默认内部存储**（这是当前未提交重构引入的字段）。

**05 · internal/model/connection.go（10 行）— 数据源连接定义**
- `SourceType`（mock/github/postgres）+ `SourceURL`（承载 owner/repo 或连接串），是工厂分流的依据。

**06 · internal/model/user.go（9 行）— 用户**
- 只存 `PasswordHash`（bcrypt），不存明文。四个模型里最简的一个。

**07 · internal/model/diff.go（10 行）— 对账差异**
- 四类差异常量 + 源/目标版本与 SHA256 Hash 字段，是对账引擎的输出结构。

### 第 3 层：引擎抽象（核心接口）

**08 · internal/engine/errors.go（7 行）— 永久错误哨兵**
- `ErrNonRetryable`：标记"重试也没用"的错误（配置写错等），Worker 捕获后直接进 DLQ。整个失败分流体系的地基。

**09 · internal/engine/source.go（16 行）— Source 接口**
- 分页契约：`Fetch(ctx, cursor, limit) → (records, nextCursor, hasMore, err)`，cursor 空串 = 从头开始。新增数据源只需实现这一个方法 + Close。

**10 · internal/engine/destination.go（24 行）— Destination 接口**
- 五个方法：`Save`（幂等批量写）+ `GetCheckpoint/UpdateCheckpoint`（断点）+ `CreateBatch/CompleteBatch`（批次进度）+ `Close`。**断点续传和进度上报的全部约定都在这里**。

**11 · internal/engine/engine.go（74 行）— 同步引擎（骨架）**
- 分页循环：检查 ctx → Fetch 一页 → Save 一页并累加 → 判 hasMore → 更新断点；`defer` 兜底：中途出错把批次标 failed。
- 设计精髓：引擎只认接口，不认任何具体实现（依赖倒置）；"崩溃最多丢一页"的保证来自"每页写完立刻落库游标"。

### 第 4 层：数据访问（repository）

**12 · internal/repository/db.go（54 行）— pgxpool 封装**
- 只负责连接池的创建/验证/关闭 + `Begin()` 事务入口。注释明说"不写 SQL"，职责单一。`Begin` 是 outbox 事务的关键设施。

**13 · internal/repository/user_store.go（29 行）— 用户表**
- `Create` / `GetByUsername` 两个方法，注册登录的落点。

**14 · internal/repository/connection_store.go（83 行）— 数据源 CRUD**
- **多租户防护的样板**：所有 SQL 都带 `WHERE id=$1 AND user_id=$2` 双条件，注释里明确"防止用户 A 改了用户 B 的数据源"。

**15 · internal/repository/job_store.go（93 行）— 任务表**
- `UpdateStatus` 里 `finished_at` 用 `CASE WHEN status IN ('completed','failed') THEN NOW()` 控制只写一次完成时间；`UpdateStatusInTx` 是事务版，给 outbox / worker 的"状态 + 消息同生共死"用。

**16 · internal/repository/outbox_store.go（52 行）— outbox 表**
- **关键约束：`Insert` 必须传外部 `tx`**——"业务写库 + 写 outbox"必须在同一事务，这是 Transactional Outbox 模式的落地。`ListUnsent` / `MarkSent` 给 Dispatcher 用。

**17 · internal/repository/synced_store.go（96 行）— 同步数据落库**
- 幂等核心：`ON CONFLICT (connection_id, id) DO UPDATE`（按"数据源+ID"去重，天然支持多源同步同一 ID）；整批包在一个事务里，原子写入。
- `ListRecordsByUser` / `ListRecordsByUserAndConnection` 分页读取，后者是对账的取数口。

**18 · internal/repository/job_destination.go（78 行）— 进度包装器（组合/装饰）**
- 把"真正的数据落点"（内部/外部）包装成完整 `engine.Destination`：`Save` 委托落点 + 累加计数写 `sync_jobs`；断点/批次读写 `sync_jobs`。
- 精妙细节：`GetCheckpoint` 时把 totalCount 和 cursor **缓存到内存**，`CreateBatch` 沿用旧值不清零——这是"崩溃重启后从断点继续、进度不丢"的关键。

**19 · internal/repository/internal_destination.go（35 行）— 内部存储适配器**
- 把 `SyncedStore` 适配成 `engine.Destination`：只真实现 `Save`（带 user/connection 归属），其余 4 个方法**空实现**（因为断点/进度由 JobDestination 管）。编译期 `var _ engine.Destination = ...` 保证实现完整。

### 第 5 层：目标端（当前重构中的可插拔部分）

**20 · internal/destination/factory.go（24 行）— 目标端工厂**
- 按 `targetConnectionID` 查连接 → switch `SourceType` 建外部目标（目前只有 postgres）；表名从 `syncContent` 冒号前截取（与源端共用 "table[:pk]" 语法）。

**21 · internal/destination/postgres/destination.go（84 行）— 外部 PG 目标**
- **表名白名单正则**（`^[a-zA-Z_][a-zA-Z0-9_]*$`）防 SQL 注入；独立连接池，`Close()` 必须调用否则泄漏；`Save` 幂等 upsert + 事务原子；断点 4 方法空实现（断点归元数据库管）。

### 第 6 层：数据源

**22 · internal/source/factory.go（56 行）— 数据源工厂**
- 按 `source_type` 分流：mock → 内存生成器；github → 解析 "owner/repo"；postgres → 传 `syncContent`。注释写了扩展新源的完整步骤（写包 + 加 case，Engine 一行不用改）。

**23 · internal/source/mock/generator.go（88 行）— 内存模拟源**
- 预生成 1000 条记录，`recordsFast` map 做 ID→下标索引；cursor 定位 + 分页。**是理解分页契约的最好参考实现**（纯内存、无外部依赖）。

**24 · internal/source/github/source.go（245 行）— GitHub Issues 数据源（最大的源实现）**
- **页码 ↔ 游标适配**：GitHub 是 `?page=N`，接口是 cursor 式，用"cursor=页码字符串"桥接；`hasMore = 本页条数 == limit`（GitHub 不返回总数，只能猜）。
- 三个实战细节：① `PullRequest *struct{}` 判 nil 过滤 PR（Issue 与 PR 共号）；② 404 包装成 `ErrNonRetryable` 直接进 DLQ，403/429（限流）保留可重试；③ body 截断 500 字防 JSONB 撑爆，`Version = updated_at.Unix()` 秒级版本号。

**25 · internal/source/postgres/source.go（136 行）— PG 表级数据源**
- **keyset 分页**：`WHERE pk::text > cursor`，主键统一 `::text` 比较，兼容任意主键类型（数值/UUID/TEXT）；表名/主键白名单正则防注入。
- 细节：`time.Parse(RFC3339Nano)` 而非 RFC3339——PG timestamptz 带微秒，用错格式 Version 恒为 0，对账会退化到 hash 比较。

### 第 7 层：协调组件

**26 · internal/redisclient/client.go（42 行）— Redis 封装**
- 只做连接创建 + Ping 验证 + 关闭，暴露底层 `*redis.Client` 给锁和熔断器用（和 `DB.Pool()` 同一套路）。

**27 · internal/mq/connection.go（122 行）— RabbitMQ 拓扑（最精巧的文件之一）**
- 完整拓扑：主交换机 → 主队列（配 `x-dead-letter-exchange`）；延迟重试队列的 DLX **指向主交换机**（消息 TTL 到期后回流主队列重试）；DLX → DLQ 死信。一条注释把整条链路画清楚：失败 Nack→DLQ；抢锁失败→延迟队列→回流。

**28 · internal/mq/message.go（28 行）— 消息体定义**
- `JobMessage`（带 `Attempt` 重试计数）+ `OutboxPayload`（多一个 `DelayMs`，0=立即、>0=延迟）。Dispatcher 靠 DelayMs 决定走哪条发送路径。

**29 · internal/mq/producer.go（84 行）— 生产者**
- `Publish`：普通发布主交换机；`PublishDelayed`：发到延迟队列 + **publisher confirm 同步等待 Broker 确认**才返回——"确认收到才敢 Ack 原消息"，这是不丢消息的最后一环。

**30 · internal/mq/consumer.go（33 行）— 消费者**
- `QoS(prefetch=1)` 限流 + 手动 Ack（`autoAck=false`），配合 Worker 的同步 Handle 实现单任务串行。

**31 · internal/mq/backoff.go（25 行）— 指数退避**
- `5s × 2^attempt`，封顶 2 分钟，加 `[0, d/2)` 随机抖动防"重试风暴"；`MaxAttempts=5` 封顶进 DLQ。

**32 · internal/lock/connection_lock.go（124 行）— Redis 分布式锁（含金量最高）**
- 抢锁 `SET NX EX`，value = `"{jobID}:{随机token}"` 凭证；续约/释放都用 **Lua 脚本原子校验凭证**（防续错锁、防删错锁）；`Owner()` 读凭证里的 jobID——这是 Worker 区分"同一任务重复投递"和"新任务触发"的依据。

**33 · internal/circuitbreaker/circuit_breaker.go（148 行）— 三态熔断器**
- 状态存 Redis hash（跨 Worker 共享）；三态 closed/open/half_open 流转全在 Lua 里原子完成；**探针令牌**（SET NX + TTL）保证冷却后只放一个 Worker 试探，令牌 35s TTL > 30s HTTP 超时（注释里专门说明这个关系）。

**34 · internal/circuitbreaker/source.go（45 行）— 熔断装饰器**
- 包一层 Source，对 Engine 完全透明；`Allow` 不放行 → 返回 `ErrCircuitOpen`（快速失败）；**`context.Canceled` 和 `ErrNonRetryable` 不计入熔断失败**（主动取消/永久错误不算数据源故障）。

### 第 8 层：Worker 编排（业务闭环）

**35 · internal/worker/dispatcher.go（71 行）— outbox 搬运工**
- 每 2 秒扫一次 `ListUnsent(20)` → 按 DelayMs 走 Publish / PublishDelayed → 成功才 `MarkSent`；发送失败不标，下轮自动重试（at-least-once，靠幂等兜底）。
- 可测性设计：producer/store 都定义成**最小接口**，单测注入 fake，不依赖真实 RabbitMQ——这是当前重构的成果之一。

**36 · internal/worker/worker.go（316 行）— 消息全生命周期（全项目核心文件）**
- 完整流程：解析 JSON → 查任务（已完成直接 Ack 跳过，幂等保护）→ 抢锁 → **失败分流**（Redis 异常→DLQ；重复投递→Ack 合并；新触发→事务里记 pending + 写 outbox 延迟重投）→ 抢到锁 → `taskCtx/hbCtx` 分离 + 心跳续约 goroutine（每 10s，lease=30s）→ `runSync` → 停心跳 → 释放锁 → **结果判定**（租约丢失→DLQ；熔断→冷却 60s 后延迟重投；永久错误→DLQ；超 5 次→DLQ；可重试→指数退避重投）。
- `runSync` 装配：源工厂 + 熔断包装 + 目标接线（nil→内部存储 / 其他→外部工厂）+ `engine.New(src, dst, 200)`。
- 所有重投路径都走"事务：更新状态 + 写 outbox"，把"丢消息"从根上杜绝。

### 第 9 层：对账引擎

**37 · internal/reconciliation/reconciler.go（164 行）— 数据对账**
- 复用 `source.NewSource` 工厂（和 Worker 同一条链路）拉源端全量 → `synced_store` 按 user+connection 拉目标端全量 → 装进两个 map → `compareMaps` 纯函数对比出四类差异（missing / extra / version / content），内容比较用 SHA256 hash 兜底。
- 可测性：`compareMaps` 是纯函数（不碰 DB/网络），单测直接喂 map 验证——重构的成果之二。

### 第 10 层：HTTP 层

**38 · internal/middleware/auth.go（77 行）— JWT 中间件**
- 包级 `jwtSecret` + `SetJWTSecret` 启动注入（空串返回错误，防弱密钥）；`AuthRequired` 解析 Bearer token → 校验 → 注入 `userID/username` 到 context；`GenerateToken` 签发。

**39 · internal/handler/auth.go（102 行）— 注册/登录**
- bcrypt(10) 哈希；登录失败统一回"用户名或密码错误"（不透露是哪个错）；注册即登录（注册成功直接发 token）。`Logout` 是无状态空实现（前端删 localStorage）。

**40 · internal/handler/connection.go（111 行）— 数据源 CRUD**
- 四个方法全是"取 userID → 绑 JSON → 调 Store → 返回"，每次操作前从 context 拿 userID，配合 Store 层的双条件 SQL 完成多租户隔离。

**41 · internal/handler/job.go（279 行）— 任务 CRUD + 启动 + 对账 + 记录查询**
- `RunJob` 是**事务性 Outbox 的前端落点**：查任务验权 → 构造 payload → 同一事务里 `Outbox.Insert` → 提交后立即返回（消息不丢、请求不阻塞）。
- `Reconcile` 触发对账并返回差异列表；`CreateJob` 校验源/目标数据源归属；`ListRecords` 分页查同步结果。

## 三、两条业务主线（按调用链串读）

**主线 A：一次同步任务从触发到完成**

```
41 handler/job.go RunJob
  → 16 outbox_store.Insert（与业务同事务）
  → 35 worker/dispatcher.go 2s 轮询到
  → 29 mq/producer.go Publish → RabbitMQ 主队列
  → 36 worker/worker.go Handle：抢锁(32) → 心跳续约(32) → runSync
      ├─ 22 source/factory → 23/24/25 具体源 → 34 熔断包装
      ├─ 20/21 destination 接线 → 18 job_destination 包进度
      └─ 11 engine.Run 分页循环 → 17 synced_store 幂等落库
  → 成功：Ack；失败：熔断/退避 → 写 outbox 延迟重投 → 超限进 DLQ(27)
```

**主线 B：一次对账**

```
41 handler/job.go Reconcile
  → 37 reconciler.Reconcile
  → 22 source.NewSource 拉源端全量
  → 17 synced_store 拉目标端全量（按 user+connection）
  → compareMaps 四类差异 → 返回前端
```

## 四、顺序复盘中的发现（按文件点名）

| 位置 | 发现 | 建议 |
|------|------|------|
| 第 1 层两个入口 | 装配都在 main 里平铺，无 `wire`/手动依赖注入 | 规模尚可接受，暂不改 |
| 38 middleware | JWT 密钥是包级变量，多实例部署需同步配置 | 已在 .env 注入，够用 |
| 41 handler | HTTP 层零测试（已知缺口） | 补主要路由的 handler 测试 |
| 36 worker.go | 316 行偏大，失败分流的判定逻辑可抽纯函数（学 dispatcher/reconciler 的做法） | 下次重构点 |
| 11 engine + 18 | `CreateBatch` 返回的 batchID 被 JobDestination 直接用 jobID 代替 | 语义上批次概念被简并，可接受但要知道 |
| 37 reconciler | `extra_in_target` 无法区分"源端删除"和"误同步" | 注释已承认，属已知限制 |
| 23 mock | 用了 Go 1.21+ 内建 `min()`，注意最低 Go 版本 | go.mod 已要求 1.26，无碍 |
| 全库 | 中文注释量大、教学味重，利于学习但偏噪音 | 上简历/开源前可清理冗余注释 |

## 五、如何用这份复盘

- **第一遍**：按第 1 → 10 层顺序只读"职责一句话"，建立地图。
- **第二遍**：按主线 A 串读 8 个关键文件（41→16→35→29→36→22→11→17），把一次同步的全链路讲给自己听。
- **第三遍**：挑 4 个含金量文件精读：**32 分布式锁、27 MQ 拓扑、33 熔断器、36 worker 生命周期**——这也是面试最可能被追问的四个点。
