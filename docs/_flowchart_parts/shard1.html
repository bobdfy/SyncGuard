10 · internal/engine/destination.go（24 行）— 数据目的地接口契约

职责：抽象"写数据 + 管断点 + 管批次"的能力，V0 唯一实现是 repository.SyncedStore（写 PG）。

Destination 接口

· Save(ctx, records []model.Record) error
　— 批量 upsert：有则更新、无则插入（ON CONFLICT DO UPDATE）
　— 幂等：同一条写两次结果一致；整批事务原子，全成功或全失败

· GetCheckpoint(ctx, taskName string) (lastCursor string, err error)
　— 读断点；查不到返回 ""（非错误），由调用方判断是否首次运行

· UpdateCheckpoint(ctx, taskName, cursor string) error
　— 每页写完后 upsert 游标（INSERT ... ON CONFLICT(task_name) DO UPDATE）

· CreateBatch(ctx) (batchID int64, err error)
　— 引擎启动时插一条 status='running' 批次记录，返回自增 ID

· CompleteBatch(ctx, batchID int64, status string, totalCount int) error
　— 引擎结束时更新 status/finished_at/total_count

· Close() error — 释放资源

关键逻辑详解

  • 六个方法覆盖引擎全部写侧需求：落库、断点读/写、批次开始/结束、资源释放。
  • 幂等性由 SQL 层保证：Save 与 UpdateCheckpoint 都基于 ON CONFLICT upsert。
  • 断点以 taskName 为键，不同任务互不干扰；首次运行 GetCheckpoint 返回空串即从头拉。

关键逻辑详解

  • 断点保证：每页先 Save 再 UpdateCheckpoint（步骤 c→e），崩溃重启从 cursor 继续，最多重复/丢失一页。
  • defer 兜底：ok 标志位——任何 return（Fetch/Save/UpdateCheckpoint 失败、ctx 取消）都会让 ok 保持 false，defer 用 context.Background()（注意不是已取消的 ctx）把批次补记为 failed，避免重复写两次。

  • 空页处理：len(records)>0 才 Save/累加，空页直接判 hasMore，避免无意义写库。
  • 边界：最后一页（hasMore=false）不调用 UpdateCheckpoint 就 break——断点已在倒数第二页推进，最后一页落库后即完成。
  • 所有错误用 fmt.Errorf(": %w") 包装向上透传，不在引擎内吞错。
